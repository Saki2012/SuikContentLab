# 一套會持續長大的系統，我會先替它留好哪三層？

> **從一年實戰整理出的 SysCore / Feature / SpecFeature 模組邊界**

有些系統的問題，不是「寫錯了」。

而是它一開始只需要把功能做出來，後來卻慢慢變成了一套要持續長大的產品。

功能一個一個加，需求一個一個疊，幾個月後再打開 Repository，常常會看到很熟悉的畫面：

- 共用工具散在各處
- 每個功能都有自己的 API 寫法
- Log、Cache、權限、錯誤處理各長一套
- 客製需求直接插進標準流程
- 同一份功能因為不同版本，開始出現大量 if / switch
- 想改一個共用行為，卻不知道到底有幾個地方需要一起改

系統還是能跑。

但開始不好改、不好查，也不好長。

這一年我在實際做一套需要長期維護、持續擴充，而且還必須容納不同產品版本的系統時，最後把架構慢慢收斂成三個主要層次：

```text
SysCore
   ↑
Feature
   ↑
SpecFeature
```

如果更精確地看依賴方向，則是：

```text
SpecFeature ───────┐
      │            │
      ▼            ▼
   Feature ────→ SysCore
```

也就是：

- **SysCore**：系統本身怎麼運作
- **Feature**：產品到底要做什麼
- **SpecFeature**：特定版本、客戶或情境要額外改什麼

前兩層我幾乎會當成基本盤。

第三層則只有在「同一套產品需要衍生不同版本」時才值得存在。

這篇不是要說三個資料夾怎麼命名。

我比較想完整講的是：

> **我怎麼判斷一段程式應該屬於哪一層，以及為什麼這個邊界值得花時間設計。**

---

## 先講最重要的：這不是 Folder Convention

如果只是把專案切成：

```text
/SysCore
/Features
/SpecFeatures
```

但程式還是到處互相引用，那其實只是把原本的混亂搬進三個比較漂亮的資料夾。

真正重要的是三件事：

1. 責任是什麼？
2. 誰可以依賴誰？
3. 這個模組換到另一套系統，還成立嗎？

我後來最常拿來判斷的問題其實很簡單：

> **「這段 Code，是在解決『系統能力』，還是在解決『業務能力』？」**

如果答案還是模糊，再補問一句：

> **「今天整個產品 Domain 換掉，這段東西還有價值嗎？」**

如果答案是「有」，它通常比較接近 SysCore。

如果答案是「沒有，因為這就是這個產品要做的事情」，它通常就是 Feature。

如果答案是「只有某一個版本或某一個客戶才需要」，那才輪到 SpecFeature。

---

# 第一層：SysCore —— 系統要怎麼活著

我心裡的 SysCore，不是 Common、Utils 或「不知道放哪就先丟進來」的垃圾桶。

它應該是一組一組有清楚責任的 **System Capability**。

例如：

```text
SysCore/
├─ Logging
├─ Security
├─ Cache
├─ DataAccess
├─ ApiTransport
├─ ErrorHandling
├─ FileStorage
├─ I18n
└─ Infrastructure...
```

這些名字不是重點。

重點是它們都有一個共同特徵：

> **它們不應該知道你的產品今天是在做內容管理、合約、會員、ERP，還是別的東西。**

---

## 我判斷 SysCore 的第一個標準：它能不能「帶走」？

這是我自己最在意的一點。

假設今天把整個產品換掉：

- Log 還是需要
- Authentication / Authorization 還是需要
- API transport 還是需要
- Error handling 還是需要
- Cache 可能還是需要
- DB access 可能還是需要

它們的使用程度會不同，但概念本身不會因為 Domain 改變而消失。

所以我會希望 SysCore 具備一定程度的：

- 可搬移
- 可替換
- 可選用
- 可縮減

注意，是「可選用」，不是每套系統都要裝企業級全家餐。

如果今天只是單機工具：

```text
Local Machine
No Cluster
No Distributed Cache
No Load Balancer
```

那就不要硬塞 Redis、Distributed Lock 或一整套分散式能力進去。

SysCore 應該讓系統可以依需求組裝，而不是逼所有專案背著同一包重量。

---

# 一個實際例子：我怎麼想「API Transport」這個模組？

這一年裡有一個很實際的問題：

同一套前端既可能跑在 Browser，也可能跑在 Server Render 的環境。

如果每一個 Feature 都自己建立 HTTP Client，就很快會出現：

- Browser 的 Base URL 一套
- Server 的 Origin 一套
- Cookie forwarding 各寫各的
- 語系 Header 各寫各的
- XSRF / CSRF 處理散在不同功能
- Retry 邏輯不一致

這時候我不會把這些東西放進某個「內容功能」或「表單功能」。

因為它根本不是業務。

它是在回答：

> **這個系統要怎麼安全、穩定地跟 Backend 溝通？**

所以這種能力我會放在 SysCore。

概念上，它的公開入口應該很窄：

```ts
interface ApiClientFactory {
    create(context: RuntimeContext): ApiClient;
}
```

裡面的實作可以自己處理：

```text
Browser
→ Cookie / XSRF
→ Client Base URL
→ Accept-Language

Server Render
→ Backend Origin
→ Cookie Forwarding
→ Accept-Language
→ Request-scoped instance
```

Feature 不應該知道這些細節。

Feature 只需要知道：

> **「我要呼叫這個業務 API。」**

這就是 Interface 的價值。

---

# Interface 不是為了「看起來很 Architecture」

我以前也看過不少專案為了抽象而抽象。

一個只有一種實作、永遠不會換的 Class，也硬要生：

```text
IFoo
Foo
FooService
FooManager
FooProvider
```

最後只是多五個檔案。

所以我現在設計 Interface，會先問它是不是在保護一個 邊界。

例如 SysCore 的 API / Repository / Cache Interface，對我來說通常是在保護這幾件事：

### 1. 隔離實作細節

Feature 不需要知道底下是：

```text
Local Cache
Redis
SQL
HTTP
File
Memory
```

它只需要知道「我可以做什麼」。

### 2. 固定共用行為

例如 API 回傳格式、錯誤處理、權限、交易、快取失效。

如果這些規則讓每個 Feature 自己決定，系統長到後面一定會出現：

```text
Feature A：這樣做
Feature B：少一個步驟
Feature C：歷史版本
Feature D：又自己包了一層
```

### 3. 讓上層可以只 Override 差異

我希望 Feature 寫的，是「業務差異」。

而不是每新增一個 Feature，就重寫一次：

- CRUD
- Transaction
- Error handling
- Mapping
- Cache eviction
- Common response
- Repository orchestration

所以後端實作上，我會讓 SysCore 提供一套 Generic Service / Controller contract。

概念大概像：

```csharp
public interface IEntityService<TAggregate>
{
    Task<TAggregate> CreateAsync(TAggregate data);
    Task<TAggregate> UpdateAsync(string id, TAggregate data);
    Task<TAggregate> QueryAsync(string id);
    Task<IReadOnlyList<TAggregate>> QueryListAsync(QueryParam query);
    Task DeleteAsync(string id);
}
```

共用生命週期由 Core 處理：

```text
Validate
↓
Begin Transaction
↓
BeforeUpdate()
↓
Repository Operation
↓
AfterUpdate()
↓
Commit
↓
Cache Eviction
↓
Response / Message
```

而 Feature 只需要處理：

```text
這筆資料在新增前，要檢查什麼？
這個 Domain 有什麼 Business Rule？
這個 Aggregate 有哪些特殊 Mapping？
```

這會直接影響維護成本。

因為「新增一個業務模組」不再等於「重新寫一套系統骨架」。

---

# 第二層：Feature —— 產品真正提供的能力

SysCore 解決的是：

> **系統怎麼運作？**

Feature 則是在回答：

> **這個產品到底要做什麼？**

所以 Feature 應該跟產品 Domain 一起長。

假設一個產品有：

```text
Article
Member
Order
Workflow
Report
```

那我會希望每一個 Feature 盡量把自己的垂直切面收好：

```text
Feature/
└─ Article/
   ├─ Model
   ├─ DTO
   ├─ Biz
   ├─ API
   ├─ Hooks
   └─ UI
```

實際專案不一定非得長這樣。

但核心概念是：

> **跟 Article 有關的東西，應該盡量在 Article 的邊界裡找到。**

而不是變成：

```text
Controllers/
Services/
Models/
DTOs/
Pages/
Hooks/
Utils/
```

然後要理解一個 Feature，得在八個大資料夾之間一直跳。

---

# 為什麼我後來偏向 Feature-oriented？

因為維護時，我真正想知道的通常不是：

> **「所有 Controller 在哪？」**

而是：

> **「這個業務功能整套到底怎麼跑？」**

當一個 RD 接到 Bug：

> **某個表單儲存後狀態不對。**

他真正要追的是：

```text
UI
↓
Feature Hook / Adapter
↓
API
↓
Biz Rule
↓
Model / Repository
```

如果這一整條鏈有清楚的 Feature 邊界，閱讀成本會低很多。

這也是 AI Coding 時代我反而更在意 Feature boundary 的原因。

AI 可以掃整個 Repository。

但清楚的邊界可以讓它更容易知道：

- 哪些檔案是同一個業務
- 哪些規則可以一起修改
- 哪些東西不該碰
- 修改後應該檢查哪一條路徑

AI 讀得快，不代表它應該被迫在一坨沒有責任邊界的 Code 裡猜。

---

# Feature 的 API 為什麼還要再經過 Adapter？

前端實作上，我後來不太希望 UI 直接碰 Axios / fetch。

因為 UI 真正想做的是：

```text
Query List
Query Detail
Create
Update
Delete
Invalid
```

而不是：

```text
POST 哪個 URL？
Response 包幾層？
錯誤訊息放在哪？
SSR 初始資料怎麼接？
CSR 重新查詢怎麼接？
Loading 怎麼統一？
```

所以我會讓 SysCore 提供 Generic API Adapter 的 contract：

```ts
interface DataService<T> {
    queryList(param): Promise<ApiResponse<T[]>>
    queryData(id): Promise<ApiResponse<T>>
    create?(data): Promise<ApiResponse<T>>
    update?(id, data): Promise<ApiResponse<T>>
    delete?(id): Promise<ApiResponse<T>>
}
```

Feature 再提供自己的 Service 實作與參數。

這裡有一個我很在意的原則：

> **Interface 應該描述「呼叫者需要什麼」，而不是把底層實作原封不動暴露出去。**

這樣 UI 才不會跟 HTTP、SSR、XSRF、Toast、Response Shape 全部黏死。

---

# 第三層：SpecFeature —— 不要讓客製需求污染標準產品

這一層是我這次實戰裡最有感的部分之一。

如果系統只有一個版本，其實完全不需要 SpecFeature。

但當產品開始變成：

```text
Standard Product
├─ Variant A
├─ Variant B
└─ Variant C
```

問題就會來了。

最容易的做法通常是：

```csharp
if (variant == "A") { ... }
else if (variant == "B") { ... }
```

一開始很快。

做三個月也還好。

做一年之後，你會得到一套「所有版本都住在同一份 Code 裡」的產品。

那時候任何修改都要問：

> **「這段到底會不會影響別人？」**

這就是我想用 SpecFeature 隔離掉的東西。

---

# SpecFeature 的設計原則：標準版先成立，客製只覆寫差異

我的方向不是：

> **每個版本 Fork 一套產品。**

而是：

```text
SysCore
   ↓
Feature（標準產品）
   ↓
SpecFeature（只放差異）
```

所以 SpecFeature 應該盡量小。

如果一個版本 90% 都跟標準版一樣，那 Spec 裡就只應該留下那 10%。

例如：

- 多一個欄位
- 多一段驗證
- 多一個特殊 API
- 替換一個 Component
- 多一個 Route
- 多一份 Asset
- 修改一小段 Business Rule

而不是複製整個 Feature 再改。

---

# 我怎麼讓 SpecFeature 不污染其他版本？

這裡只講概念，不放實際專案名稱。

我最後採用的是 **Build-time Variant Selection**。

也就是在 Build 時先指定：

```text
CurrentVariant = A
```

然後：

### Backend

編譯時：

```text
移除所有 SpecFeature
↓
只把 CurrentVariant 的 SpecFeature 加回編譯
↓
其他 Variant 留在 Repository，但不進這次產物
```

好處是：

> **A 版本的客製 Code，根本不會被編進 B 版本的 Binary。**

不是 Runtime 才判斷「這段要不要跑」。

是它根本不存在於那份產物裡。

### Frontend

概念也一樣。

Build 時用 Alias 把：

```text
SpecFeature
```

指到：

```text
SpecFeatures/{CurrentVariant}
```

所以 Feature 端只需要知道：

> **「如果目前 Variant 有這個 Slot，就使用它；沒有就 fallback Core / Feature。」**

概念上：

```ts
const View = resolveSpecComponent(
    "Article/View.tsx",
    DefaultArticleView
)
```

最後效果就是：

```text
Spec 有覆寫
→ 用 Spec

Spec 沒覆寫
→ 回 Feature / Core
```

這個模式我後來拿來處理：

- Component
- Function
- Asset
- Route Extension
- Registry Extension

它的好處不是「很炫」。

而是客製需求終於有一個明確的家。

---

# 為什麼不直接做大量 if / switch？

因為 if / switch 最大的問題不是醜。

而是它會讓「版本差異」滲透到所有層。

最後你可能在：

```text
UI
Biz
DTO
API
Route
CSS
Asset
```

每個地方都看到：

```text
if VariantA
if VariantB
if VariantC
```

這時候版本已經不再是模組。

而是整套系統的環境污染。

SpecFeature 的目的，就是把這個污染收斂回一個邊界。

---

# 那 Backend 怎麼擴充 Feature？

Backend 我用了兩種很實用的方式。

## 1. Override Hook

Feature 先把共用流程做好：

```csharp
protected virtual Task BeforeUpdate(...)
protected virtual Task AfterUpdate(...)
```

Spec 只 Override 差異：

```csharp
protected override Task BeforeUpdate(...)
{
    await base.BeforeUpdate(...);

    // Variant-specific rule
}
```

好處是標準流程仍然只有一份。

Spec 不需要複製 CRUD / Transaction / Repository orchestration。

## 2. Partial Extension

如果只是：

- 多欄位
- 多一個 DTO property
- 多一個 API endpoint

那可以透過 partial 類型把 extension 放在 SpecFeature。

Feature 仍然維持自己的核心定義。

這兩種方式讓我可以依「差異大小」選擇擴充方法，而不是每次都 Fork 整個 Feature。

---

# 三層之間，我最想守住的 Dependency Rule

理想上，我會希望方向是：

```text
SpecFeature → Feature → SysCore
      └────────────→ SysCore
```

反方向則盡量不要發生：

```text
SysCore ✕→ Feature
Feature ✕→ SpecFeature
SysCore ✕→ SpecFeature
```

原因很簡單。

如果 SysCore 開始知道某個業務：

> **它就不再是 Core 了。**

如果 Feature 開始知道某一個版本：

> **它就不再是 Standard Feature 了。**

實戰上，我現在這套系統也不是 100% 純潔。

一年演進下來，仍然有少數歷史位置存在 Core 反向引用 Feature、共用基底知道太多業務類型等情況。

但這反而讓我更確定：

> **Dependency Direction 不是潔癖，而是一個需要持續守的預算。**

每多一次反向依賴，未來搬移、測試、替換與拆分的成本就會增加一點。

架構不是一次設計完就永遠乾淨。

它比較像是在長期開發中，不斷把偏掉的邊界拉回來。

---

# 那到底怎麼判斷一個新模組要放哪？

我現在會用這幾個問題快速判斷。

## 放 SysCore 前問：

- 換一個產品 Domain，它還成立嗎？
- 它是在處理技術能力，而不是業務規則嗎？
- 它可以被替換或移除嗎？
- 它有辦法只透過 Interface 被上層使用嗎？
- 它會不會開始 import 某個 Feature 的 Model？

最後一題如果答案是「會」，我通常會再想一次。

## 放 Feature 前問：

- 它是不是產品對使用者提供的一個能力？
- 它有自己的資料、流程或 Business Rule 嗎？
- 我能不能用一個 Domain 名字描述它？
- RD 要理解這個功能時，相關 Code 是否能集中找到？

## 放 SpecFeature 前問：

- 標準產品真的不需要它嗎？
- 它是不是只屬於某一個版本 / 客戶 / 情境？
- 能不能只放「差異」，而不是複製整個 Feature？
- 如果未來取消這個 Variant，刪掉整個 Spec 目錄是否就能回到標準版？

如果最後一題做不到，通常代表客製邏輯已經漏回 Feature 了。

---

# 這套設計一年後，我實際得到什麼？

不是「資料夾比較漂亮」。

真正有感的是下面幾件事。

## 1. Debug 範圍變小

出問題時可以先判斷：

```text
系統能力？
→ SysCore

標準業務？
→ Feature

只有某版本出問題？
→ SpecFeature
```

排查方向會比「整個 Repository 都有可能」清楚很多。

## 2. 新 Feature 不需要重新發明系統能力

API、錯誤、權限、Repository、共用 CRUD、Cache 等規則可以沿用。

RD 比較能把時間花在 Business Rule。

## 3. 客製需求不再一直污染標準產品

差異集中後，升級標準 Feature 時比較敢動。

## 4. AI Coding 的 Context 更容易控制

可以直接告訴 Agent：

```text
這次只處理 Feature X
不要改 SysCore
Current Variant 是 Y
只允許在 SpecFeature Y 覆寫差異
```

這種 Boundary 對 AI 其實非常重要。

## 5. 架構開始變成團隊共同語言

最重要的是大家可以開始問：

> **「這個應該是 Core、Feature，還是 Spec？」**

只要這句話能被團隊共同理解，很多 Review 的討論就會快很多。

---

# 這套架構也有代價

我不會說這是所有專案都該照抄的答案。

它的成本其實很明確。

### 1. 前期設計成本比較高

小專案如果三個月就結束，可能根本不值得做這麼多邊界。

### 2. SysCore 很容易變成另一個垃圾桶

「大家都會用」不等於「應該放 Core」。

沒有 ownership 的 Core，最後只是 Common 2.0。

### 3. Generic Framework 很容易長太大

共用 CRUD、Adapter、Controller 很方便。

但一旦為了 cover 所有 Feature 而開始塞一堆例外，Core 本身也可能變成 God Object。

所以我會要求：

> **特殊 Business Rule 優先留在 Feature，不要為了一個例外污染 Generic Core。**

### 4. SpecFeature 很容易失控成 Fork

如果每個版本的 Spec 都複製大量 Feature，這套設計就失去意義。

Spec 的核心原則一直都是：

> **只保存差異。**

---

# 最後：我現在把三層看成什麼？

做了一年之後，我已經不太把它們看成資料夾。

我會把它們看成三種不同的「變化速度」。

```text
SysCore
→ 變得最慢
→ 穩定、共用、可搬移

Feature
→ 跟著產品演進
→ 持續增加 Business Capability

SpecFeature
→ 跟著特定版本 / 客戶變化
→ 可以獨立增加，也可以整包移除
```

這也是我現在認為一套「會持續長大的系統」最需要先想清楚的事情：

> **不是今天有哪些功能，而是不同種類的變化，未來要被關在哪些邊界裡。**

當這件事情有答案之後，

SysCore / Feature / SpecFeature 才不只是命名。

它會慢慢變成這套系統自己的 Framework。
